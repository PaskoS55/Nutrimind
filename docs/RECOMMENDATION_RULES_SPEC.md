# NutriMind by Pasko — Recommendation Rules Specification

Версия: `0.1.1-draft`  
Статус: архитектурная основа для проверки; не для публикации и реальных пользователей  
Связанные документы: [`NUTRIMIND_SURVEY_SPEC.md`](./NUTRIMIND_SURVEY_SPEC.md), [`CALCULATION_CORE_SPEC.md`](./CALCULATION_CORE_SPEC.md), [`PRODUCT_DATABASE_SPEC.md`](./PRODUCT_DATABASE_SPEC.md)

## 1. Назначение и неизменяемые приоритеты

Документ описывает детерминированный подбор продуктов, замен и демонстрационного дневного рациона. Любая рекомендация проходит безопасность до оценки пищевой ценности.

Порядок приоритетов не меняется:

```text
аллергия
→ медицинское ограничение
→ неизвестные данные безопасности
→ самостоятельно исключённый продукт
→ непереносимость
→ цель и расчётные потребности
→ нелюбимые продукты
→ удобство и разнообразие
```

Низший приоритет никогда не может вернуть продукт, исключённый более высоким.

## 3. Конвейер подбора

Каждый этап получает результат предыдущего. Пропуск этапа запрещён.

| № | Этап | Результат |
|---:|---|---|
| 0 | Валидация анкеты и версий | корректный вход или `blocked` |
| 1 | Возрастной и медицинский шлюз | допустимый уровень персонализации |
| 2 | Жёсткий фильтр аллергий | только продукты без аллергенного конфликта |
| 3 | Медицинский шлюз | `allowed`, `blocked` или `specialist_review` |
| 4 | Фильтр непереносимостей | подходящие технологические варианты |
| 5 | Самостоятельные исключения | удаление продуктов и производных |
| 6 | Нелюбимые продукты | понижение рейтинга или исключение из меню |
| 7 | Формирование кандидатов по пищевой роли | набор продуктов для конкретной задачи |
| 8 | Рейтинг кандидатов | стабильная оценка `0–100` |
| 9 | Разнообразие и совместимость меню | конечный набор без повторов и конфликтов |
| 10 | Объяснение и аудит | цепочка `ответ → правило → коэффициент → результат` |

## 4. Валидация до фильтрации

Система возвращает `blocked`, если:

- `none` выбран вместе с конкретной аллергией, непереносимостью или медицинским ограничением;
- спортивная ветка не содержит обязательных спортивных ответов;
- обычная ветка не содержит `activity`;
- значение `другая аллергия` не сопоставлено с нормализованным аллергеном;
- отсутствует версия анкеты, расчётного ядра или базы;
- набор продуктов не содержит достаточной информации об ингредиентах и аллергенах.

Система не исправляет конфликтующие ответы автоматически.

## 5. Аллергии — абсолютный фильтр

### 5.1. Решение по связи продукта с аллергеном

| `food_allergen.relation` | Решение при совпадении с аллергией |
|---|---|
| `contains` | исключить |
| `derived_from` | исключить |
| `may_contain` | исключить |
| `cross_contact` | исключить |
| `unknown` | исключить |
| сведения отсутствуют | исключить как `safety_unknown` |
| `free_from_claim` | допустить только при актуальной проверенной маркировке и полном составе |

Для рецепта проверяются блюдо, каждый ингредиент и все вложенные составные ингредиенты. Успешная проверка верхнего уровня не отменяет проверку нижних.

```text
Ответ пользователя: аллергия на молоко
→ Правило ALLERGY.MILK.001: исключить milk и производные
→ Коэффициент допуска: 0
→ Результат: обычный и безлактозный йогурт не участвуют в рейтинге
```

```text
Ответ пользователя: аллергия на арахис
→ Правило ALLERGY.PEANUT.002: may_contain также небезопасен
→ Коэффициент допуска: 0
→ Результат: батончик «может содержать арахис» исключён
```

### 5.2. Отдельные группы

- `tree_nut:*` не включает арахис автоматически;
- `fish:*` не включает ракообразных и моллюсков;
- `seafood` из анкеты включает `crustacean:*` и `mollusc:*`, но не рыбу;
- `wheat` и целиакия — разные правила: аллергия на пшеницу блокирует пшеницу, целиакия включает строгий фильтр всех глютенсодержащих злаков и перекрёстного контакта;
- кунжут проверяется также в тахини, смесях специй, соусах и хлебобулочных ингредиентах;
- нераспознанная «другая аллергия» блокирует продукты, замены и меню целиком.

### 5.3. Псевдокод

```text
function allergyEligible(product, userAllergens):
  if userAllergens is empty:
    return product.safety_status != "blocked"

  if product.safety_status in ["unknown", "partial", "blocked"]:
    return false

  relations = resolveAllergenRelationsRecursively(product)

  for allergen in userAllergens:
    match = relations.for(allergen)
    if match is missing:
      return false
    if match.relation in [
      "contains", "derived_from", "may_contain",
      "cross_contact", "unknown"
    ]:
      return false

  return true
```

## 6. Трёхсоставный медицинский шлюз

Медицинский ответ не используется для постановки диагноза или самостоятельной лечебной диеты.

```text
MedicalDecision = allowed | blocked | specialist_review
```

| Решение | Когда | Поведение |
|---|---|---|
| `allowed` | релевантного ограничения нет или структурированное правило разрешает продукт | продолжить фильтрацию |
| `blocked` | прямой конфликт, например глютен при указанной целиакии | статус `исключён`, Score отсутствует |
| `specialist_review` | ограничение есть, но автоматическое решение небезопасно | не включать в персональное меню до проверки |

| Ответ | Автоматическое поведение |
|---|---|
| Целиакия | глютен и перекрёстный контакт → `blocked`; проверенный gluten-free → `allowed` |
| Нарушения углеводного обмена | лечебное ранжирование → `specialist_review`; снижение энергии отключено |
| Заболевания почек | белковая/минеральная роль → `specialist_review` |
| ЖКТ | без явного ограничения → `specialist_review`, а не исключение по догадке |
| Липидный обмен | лечебное ранжирование жиров → `specialist_review` |
| Повышенное давление | лечебная цель по натрию → `specialist_review` |
| Другое | `specialist_review` до структурированной классификации |

Явная рекомендация врача хранится как ограничение более высокого приоритета, но не интерпретируется свободным текстом без подтверждения структурированным правилом.

## 7. Непереносимости, исключения и предпочтения

### 7.1. Непереносимости

Непереносимость применяется после аллергий:

- лактоза → допускаются только варианты с проверенным `lactose_free_certified`, если нет аллергии на молоко;
- глютен → подбираются проверенные безглютеновые варианты, но это не приравнивается к диагностированной целиакии;
- фруктоза и бобовые → исключаются только явно сопоставленные продукты; система не расширяет список по предположению;
- «другая» → меню блокируется до нормализации ответа.

```text
Ответ: непереносимость лактозы, аллергии на молоко нет
→ Правило INTOLERANCE.LACTOSE.001
→ Коэффициент допуска: 1 для lactose_free_certified, 0 для contains_lactose
→ Результат: конкретный branded-йогурт может участвовать в рейтинге
  только после проверки актуальной маркировки
```

### 7.2. Самостоятельно исключённые продукты

Исключается:

1. сам продукт;
2. однозначные синонимы;
3. рецепт, где продукт является ингредиентом;
4. явно указанная пользователем группа.

Система не расширяет исключение на целую биологическую группу без основания. Например, исключение чечевицы не означает автоматическое исключение всех бобовых.

### 7.3. Нелюбимые продукты

- в списке рекомендуемых продуктов: штраф к рейтингу `−30`;
- в автоматическом меню: исключение;
- если подходящей замены нет: продукт не возвращается, а результат получает `candidate_shortage`.

## 8. Пищевые роли

Продукт оценивается не как «полезный вообще», а на конкретную роль:

| Роль | Примеры критериев |
|---|---|
| `protein_anchor` | белок на порцию, качество данных, удобство |
| `carb_base` | углеводы на порцию, клетчатка, пригодность вокруг нагрузки |
| `produce_source` | овощи/фрукты, разнообразие групп |
| `fat_source` | ненасыщенные жиры, удобная порция |
| `hydration_support` | жидкость и уместность во время/после нагрузки |
| `pre_training` | переносимость, умеренная клетчатка/жир, доступные углеводы |
| `post_training` | сочетание углеводов и белка, срок после нагрузки |
| `fibre_support` | вклад в клетчатку с учётом переносимости |

Один продукт может иметь несколько ролей. Нутриентная плотность не отменяет фильтры безопасности.

## 9. Последовательный допуск и рейтинг

### 9.1. Решения до рейтинга

```text
1. AllergyDecision       = allowed | blocked
2. MedicalDecision       = allowed | blocked | specialist_review
3. IntoleranceDecision   = allowed | blocked
4. UserExclusionDecision = allowed | blocked
5. DataDecision          = allowed | blocked_for_all |
                            blocked_for_allergic_user | blocked_for_role
```

Правила:

1. любой hard block → `исключён`, Score не рассчитывается;
2. `specialist_review` удерживает продукт вне персонального результата;
3. `blocked_for_allergic_user` действует только при аллергии;
4. `blocked_for_role` запрещает конкретную пищевую роль;
5. только полностью допущенный кандидат получает Score.

### 9.2. Полнота данных

| Неполнота | С аллергией | Без аллергии |
|---|---|---|
| Нет полного состава или аллергенной декларации | блокировать | разрешить общую нутриентную роль без заявления о безопасности по аллергенам |
| Нет данных о возможных следах | блокировать | добавить `allergen_data_limited` |
| Противоречивые аллергенные сведения | блокировать для всех | блокировать для всех |
| Неверная идентичность, единицы или значения | блокировать для всех | блокировать для всех |
| Нет обязательного нутриента | блокировать роль | блокировать роль |
| Нет происхождения данных | блокировать для всех | блокировать для всех |

### 9.3. Формула Score

```text
Score =
  0,30 × NutrientFit
  + 0,20 × GoalFit
  + 0,15 × MealFit
  + 0,10 × Practicality
  + 0,10 × PreferenceFit
  + 0,10 × Diversity
  + 0,05 × DataQuality
```

Все компоненты нормируются в диапазоне `0–100`.

| Компонент | Определение |
|---|---|
| `NutrientFit` | вклад обычной порции в недостающую пищевую роль, без медицинских выводов |
| `GoalFit` | соответствие типу дня и расчётным диапазонам |
| `MealFit` | пригодность для выбранного приёма пищи и времени нагрузки |
| `Practicality` | доступность, время приготовления, бытовая порция |
| `PreferenceFit` | `100` нейтральному/любимому, `70` нелюбимому до исключения из меню |
| `Diversity` | бонус новой категории относительно уже выбранных продуктов |
| `DataQuality` | `A=100`, `B=80`, `C=60`, `D=30`; `blocked` не допускается |

Округление: до одного десятичного знака. При одинаковом балле порядок определяется:

1. более высоким `DataQuality`;
2. меньшим числом предупреждений;
3. лексикографически по неизменяемому `product_id`.

Поэтому один набор ответов и одна версия данных всегда дают одинаковый результат.

### 9.4. Пороги статусов продуктов

| Статус | Точный порог/условие |
|---|---|
| `рекомендуется` | Score `80,0–100,0` |
| `подходит` | Score `65,0–79,9` |
| `нейтрален` | Score `50,0–64,9` |
| `стоит ограничить` | Score `0,0–49,9` либо явное ограничивающее правило |
| `исключён` | любой hard block; Score отсутствует |

`specialist_review` — служебное решение, а не рейтинговый статус. Ограничивающее правило ограничивает Score максимумом `49,9`. Hard block нельзя компенсировать высоким баллом.

```text
if hardBlock: "исключён"
else if limitRule or score < 50,0: "стоит ограничить"
else if score < 65,0: "нейтрален"
else if score < 80,0: "подходит"
else: "рекомендуется"
```

## 10. Выбор набора и разнообразие

1. Кандидаты группируются по пищевой роли.
2. Для каждой роли выбирается продукт с максимальным баллом.
3. Одна категория не может занимать более двух позиций в дневном меню, если есть безопасная альтернатива с баллом не ниже чем на `10` пунктов.
4. Один и тот же основной продукт не повторяется более двух раз в день.
5. Минимум три разные группы овощей и фруктов предлагаются только при наличии безопасных кандидатов.
6. При нехватке кандидатов система уменьшает полноту меню, но не ослабляет фильтр.

## 11. Подходящие замены

Замена должна:

- пройти все фильтры заново;
- сохранить ключевую пищевую роль;
- иметь сопоставимую бытовую порцию;
- не создавать новый аллергенный или медицинский конфликт;
- показывать, что именно сохраняется.

```text
Ответ: арахис исключён аллергией
→ Правило REPLACEMENT.001: искать безопасную роль fat_source
→ Коэффициент допуска: 0 для арахиса и may_contain; 1 для проверенного кандидата
→ Результат: проверенная паста из семян подсолнечника,
  только если в ней нет кунжута, арахиса и предупреждения о следах
```

Замена «похожая по названию» без сопоставления роли запрещена.

## 12. Объяснение рекомендации

Каждая карточка продукта содержит:

```yaml
because_of:
  answer:
    question_id: string
    value: any
  rule:
    id: string
    version: string
    text: string
  coefficient:
    name: string
    value: number | string
  result:
    metric: string
    value: string
safety_checks:
  allergies: passed
  medical: allowed | blocked | specialist_review
  intolerances: passed
  data: allowed | blocked_for_all | blocked_for_allergic_user | blocked_for_role
source:
  product_record_version: string
```

Пример:

```text
Ответ: белковый продукт 2 раза в день; профессиональный спортсмен
→ Правило PRIORITY.PROTEIN_FREQUENCY.001: усилить роль protein_anchor
→ Коэффициент NutrientFit: 92/100
→ Результат: добавить проверенный branded-безлактозный йогурт как один из вариантов

Проверка безопасности:
аллергия на арахис — пройдена;
непереносимость лактозы — пройдена по lactose_free_certified;
данные о возможных следах арахиса — проверены.
```

## 13. Формулировки о рисках

Разрешено:

- «по ответам белковый продукт появляется реже, чем удобно для выбранной спортивной нагрузки»;
- «возможен риск недостаточного поступления из текущего рациона»;
- «если низкая энергия сохраняется, стоит обсудить это со специалистом»;
- «без числового результата анализа дефицит подтвердить нельзя».

Запрещено:

- «у вас дефицит»;
- «у вас анемия / диабет / заболевание ЖКТ»;
- «этот продукт лечит»;
- «анализ подтверждает», если анкета содержит только название анализа;
- создавать медицинскую рекомендацию из корреляции симптомов и питания.

## 14. Демонстрационный сценарий спортсмена

Вход: мужчина, 28 лет, профессиональный хоккеист, 86 кг, вечерняя тренировка 90 минут, арахисовая аллергия, непереносимость лактозы, белковый продукт два раза в день, мало овощей и фруктов, поздний приём пищи после нагрузки, 1,5–2 л жидкости, выраженное потоотделение, свежих анализов нет.

Результат конвейера:

1. все продукты с арахисом, производными и возможными следами удалены;
2. молочные продукты с лактозой удалены, проверенные безлактозные могут остаться;
3. роли `post_training`, `protein_anchor`, `produce_source` и `hydration_support` получают повышенный приоритет;
4. предлагаются варианты приёма пищи после нагрузки, но не диагноз причины спадов энергии;
5. в отчёте используется «возможный риск недостаточного поступления», а не «дефицит»;
6. отсутствие анализов исключает подтверждённые лабораторные выводы.

## 15. Версионирование и аудит

Каждый результат сохраняет:

```text
survey_spec_version
calculation_core_version
recommendation_rules_version
product_database_version
product_record_versions[]
generated_at
input_hash
ordered_rule_trace[]
```

Изменение формулы, веса рейтинга или поведения фильтра создаёт новую версию. Старый отчёт должен воспроизводиться на исходных версиях.

## 16. Критерии приёмки

- запрещённый аллерген не появляется в продукте, замене, рецепте или меню;
- `unknown` никогда не трактуется как `safe`;
- медицинский флаг не порождает самостоятельное лечение;
- медицинское решение всегда одно из `allowed`, `blocked`, `specialist_review`;
- фильтр применяется до рейтинга;
- используются точные пороги статусов версии `0.1.1`;
- неполнота данных блокирует только документированную область;
- объяснение содержит исходный ответ, правило, коэффициент и результат;
- одинаковый вход и версии дают одинаковый упорядоченный список;
